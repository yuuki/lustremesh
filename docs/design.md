# lustremesh 設計メモ(ドラフト)

Lustre の各クライアントから個々の OST・MDT へ小さな固定形状のプローブを打ち、
クライアント × ターゲットの成否とレイテンシを Prometheus に出すツールの設計案。
M0(`lustremesh check`)だけが実装済みで、実装状況は §15 にある。
「実機で確かめること」(§12)が済むまで設計は確定ではない。

事実関係の出典は 2 種類ある。

- Lustre の挙動: lustre-release の 2.12.9 / 2.14.0 / 2.15.8 / 2.16.1 / 2.17.0 のソースと
  Operations Manual を読んだ結果。**実機では何も走らせていない。**
- 先行事例: Web 調査の結果。ベンダーの非公開マニュアルは読めていない。

## 1. 目的と非目的

目的

- ジョブの I/O が無くても、各ターゲットへの I/O 経路が生きているか、遅くないかを知る。
- 遅い・失敗する原因を、クライアント側、個別の OST、OSS、MDS・全体のどれかに切り分ける。
- 全クライアントで動かしてもファイルシステムの負荷にならない。

非目的

- スループットのベンチマーク(`ost-survey`、IOR の領分)。
- サーバ側メトリクスの収集、Lustre の設定変更、自動修復。
- 受動観測の置き換え。`lustre_client_exporter` と `lustre-ebpf-exporter` はそのまま併用する。

## 2. 先行事例との差分

最も近いのは Kaleidoscope の "Store Pings"(Jha ら、SC20、Blue Waters)。
OST に固定したファイルへ 64 バイトの `O_DIRECT` 書き込みを毎分打ち、
確率的グラフィカルモデルで故障箇所を推定する。引用と差別化が必須。

| | Kaleidoscope | lustremesh |
|---|---|---|
| 監視ノード | 6 台に限定(設計上の制約) | 全クライアント(負荷予算で抑える) |
| 公開状況 | ソフトウェアは非公開、データは公開 | OSS |
| 出力 | Jenkins から起動、独自集計 | Prometheus メトリクス |
| プローブ | データ書き込み、create+write+remove | ターゲット別 RPC、データ write/read、MDT 固定の mkdir/rmdir |
| 推定 | 同時推論(PGM) | v1 はピア比較の記録ルール、同時推論は後回し |

そのほか、富岳は「全 OST への dd 書き込み時間の定期監視」を運用している(LUG 2020、詳細不明)。
全クライアントから個々のターゲットを能動的に打つ公開ツールは、調査した範囲では見つからなかった。

同論文の負荷計測は設計の前提になる。監視 6 台・毎分ではスループット低下 0.01% 未満、
100 台・30 秒間隔ではピーク IOR 下で 2.42% だった。

## 3. 全体構成

- **エージェントのみ。** ターゲット一覧はクライアントがローカルに読めるので、
  `rpingmesh` のようなコントローラと ping リスト配布は置かない。
- **切り分けは Prometheus の記録ルール。** 行列の集計はクエリ側で行う。
- **Go、cgo なし、Apache-2.0。** Lustre との接点は次の 3 つに限る。
  - sysfs・procfs のパラメータファイルの読み取り
  - 通常の POSIX I/O(`open`、`pread`、`pwrite`、`mkdir`、`rmdir`)
  - 準備時だけ `lfs` コマンドの実行
- **liblustreapi と ioctl 構造体は使わない。** liblustreapi は 2.16 まで GPL-2.0-only、
  UAPI ヘッダも 2.15 まで GPL-2.0-only の表記である。
  `lustre_client_exporter` のクリーンルーム方針(`docs/license-policy.md`)をそのまま引き継ぐ。

サブコマンド

| コマンド | 実行者 | 役割 |
|---|---|---|
| `lustremesh init` | 管理者(一度だけ) | プローブ用ディレクトリの作成と検証 |
| `lustremesh agent` | 各クライアントの常駐サービス | プローブと `/metrics` |
| `lustremesh check` | 誰でも | 全ターゲットを 1 回ずつ打って表を出す(デバッグ用) |
| `lustremesh gc` | 管理者 | 撤去済みクライアントのファイルを削除 |

## 4. プローブの定義

3 種類を使い分ける。主役は data、ゲート兼到達性確認が rpc、MDT の実経路が meta。

### 4.1 rpc(OST・MDT、読み取りのみ)

- **操作**: `/sys/fs/lustre/{osc,mdc}/<dev>/kbytesfree` を `read` する。
  この読み取りは対象ターゲットへ statfs RPC を送る(sysfs、0444、非特権で読める)。
- **計時範囲**: `read` の 1 回。
- **未接続のとき**: ブロックせず `EAGAIN` で返る。結果は `disconnected`。
- **アイドル切断中の OSC**: 再接続してから応答を待つ。この再接続時間は rpc に含まれる。
- **限界**:
  - OST 側では I/O とは別のサービス(オブジェクト事前作成と同じスレッド群)が、
    1 秒キャッシュから応答する。ディスクには触れない。
  - クライアント側にも 1 秒キャッシュがあり、RPC を送らずに返ることがある。
    同じターゲットを 2 秒以内に他者が読んだ直後が該当する。
- **キャッシュ応答の扱い**: サンプルにしない。判定は 2 段階にする。
  - debugfs が読めるとき: `stats` の `ost_statfs` / `mds_statfs` の増分で RPC の有無を確認する。
  - 読めないとき: 下限値未満の所要時間を `cached` として捨てる(下限値は実機で決める)。

### 4.2 data(OST、write と read)

- **対象**: クライアントごと・OST ごとの 1 ページのファイル(§5)。
- **手順**:
  1. rpc プローブを先に打つ(ゲート)。`disconnected` なら data は打たない。
  2. `open(O_DIRECT)`。MDS だけが関わる。所要時間は副次サンプル `op="open"`(§4.3)。
  3. 検証(`verify`)。自分の所有でリンク数 1 の通常ファイルであること、
     `lfs getstripe` で 1 ストライプの単純なレイアウトが目的の OST にあること(§5.1)。
     属性やレイアウトの取得は OST を待つことがあるので、`open` とは別のステップにする。
  4. `pwrite` を 1 ページ。**write サンプル**。
  5. `pread` を 1 ページ。**read サンプル**。内容を照合する。
  6. `close`。
- **ゲートの効果**:
  - 未接続のターゲットで I/O がハングするのを避ける。
  - アイドル切断からの再接続を rpc 側に吸収させ、data を常に接続済みの状態で測る。
- **整列**: オフセット・長さ・バッファをすべてページサイズの倍数にする。
  2.12 の制約に合わせると全バージョンで通る。ページサイズは実行時に取得する。
- **ペイロード**: マジック、クライアント ID、連番、時刻。read で連番を照合し、
  食い違えば結果は `mismatch`。
- **write が測るもの**: OST の応答まで。ソース上は応答がジャーナルのコミットを含む
  (確度は中〜高、マニュアルと既定値の記述が食い違う箇所あり)。
- **read が測るもの**: RPC と OSS の I/O スレッド。OSS のキャッシュから返ることがあるので、
  ディスクの読み出しを測っているとは限らない。
- **クライアント側の待ち**: `O_DIRECT` の RPC は OSC の `max_rpcs_in_flight`(既定 8)の
  枠に入る。同じ OST へジョブが大量に I/O していると、その後ろに並ぶ。
  これは「このノードのジョブが体感する遅さ」として意図的に含める。

### 4.3 meta(MDT、既定で無効)

- **操作**: MDT に固定したディレクトリの中で `mkdir` と `rmdir` を 1 回ずつ。
  それぞれ別のサンプル。OST は関与しない。
- **既定で無効にする理由**: changelog の利用者が登録されていると、`MKDIR` と `RMDIR` が
  既定マスクで記録される。Robinhood などを運用しているサイトではプローブの記録が流れ込む。
- **有効化の目安**: changelog の利用者がいないサイトでは有効を推奨する。
  MDS は Lustre で最も詰まりやすく、実経路を測る価値が高い。
- **無効のときの代替**: MDT への rpc プローブ(§4.1)は常に有効。
  加えて、data の `open` の所要時間を副次サンプル `op="open"` として記録できる。

### 4.4 サンプルの条件(契約)

- レイテンシのサンプルは、完了して成功した操作だけ。
- タイムアウトは結果として数え、レイテンシには入れない。
  後で完了した場合の実所要時間は別メトリクスに出す(§7)。
- **スケジューリング遅延の検査**: 計算ノードは全コアがジョブで埋まる。
  計時の前後で `/proc/thread-self/schedstat` の実行待ち時間を読み、
  プローブ中の実行待ちがしきい値を超えたら結果を `contended` にしてレイテンシから外す。
  差し引いて補正はしない。
  - **限界**: 見えるのはプローブを打つスレッドの実行待ちだけである。RPC の送信と完了を
    担う Lustre のカーネルスレッド(ptlrpcd、LNet)が CPU を待たされた分は検出できず、
    その場合のサンプルは膨らんだまま `ok` になる。ノード全体の CPU 圧迫
    (`/proc/pressure/cpu` など)を併せて見る案は M1 で検討する。
- 取れなかった値は系列を出さない。0 で埋めない。

## 5. ファイルシステム上の配置と準備

```
<probe-root>/                         lustremesh ユーザー所有
  v1/
    ost/<OST番号>/<クライアントID>     通常ファイル、1 ページ、OST 固定
    mdt/<MDT番号>/<クライアントID>/    ディレクトリ、中で "p" を mkdir/rmdir
```

OST 番号・MDT 番号は、デバイス名に現れる 16 進表記そのまま(`0003`)とする。

### 5.1 OST への固定

- `lfs setstripe -c 1 -o N <file>` で作る。**`-i N` は使わない。**
  `-i` は開始位置の指定でしかなく、N が使えないと MDS が黙って別の OST に置く。
  `-o` は厳密で、置けなければ失敗する。
- 作成後に `lfs getstripe -i` で読み返し、N と一致しなければファイルを消して
  そのターゲットを `unprepared` にする。打たない。
- 読み返しは次の場合の保険でもある。
  - 2.16 以降で `enable_setstripe_gid` が制限されていると、ioctl が何もせず成功を返す。
  - 2.15 以降は、親のデフォルトプールに N が無いとプール指定が黙って外れる。
- `init` は probe-root にデフォルトプールや PFL のデフォルトレイアウトが
  付いていないことを検査する。
- 新規作成が止められている OST(`max_create_count=0`)では作成が失敗する。
  既存ファイルへのプローブは続ける。

### 5.2 MDT への固定

- `lfs mkdir -i N` は MDS から見た `CAP_SYS_ADMIN`、または
  `mdt.*.enable_remote_dir_gid` に一致する gid が要る(既定は 0)。
  2.16 以降は nodemap の `dne_ops` ロールも要る。
- そのため MDT ディレクトリは `lustremesh init` が作る。
  root squash が掛からない管理ノードで管理者が一度だけ実行する。
- エージェントは配下に自分のディレクトリを通常の `mkdir` で作り、
  `lfs getdirstripe -i` で MDT を読み返す。
- MDT が増設されたら `init` を再実行する。それまでその MDT は `unprepared`。

### 5.3 クライアントのファイル

- クライアント ID はホスト名を正規化したもの。
- 1 クライアント × 1 OST あたり 1 ページ、1 オブジェクト。
  1000 クライアント × 100 OST で 10 万オブジェクト、論理 400 MB 程度。
- エージェントは自分のファイル以外を消さない。
  撤去済みクライアントの分は `lustremesh gc --older-than` で管理者が消す。

## 6. ハング対策とプロセスモデル

前提となる事実

- ターゲットに届かないとき、クライアントの I/O は復旧まで待ち続ける。
- **2.14 以降、`O_DIRECT` の完了待ちは `SIGKILL` でも中断できない。**
- statfs や mkdir の同期 RPC は、復旧待ちの間かタイムアウト境界でだけシグナルを受ける。

設計

- **スーパーバイザ**: スケジュール、集計、`/metrics`。Lustre には一切触らない。
- **ワーカー**: 同じバイナリを再実行した子プロセス。Lustre に触るのはここだけ。
  rpc の読み取りと準備時の `lfs` 実行もワーカー内で行う。
- 通常はワーカー 1 つがプローブを 1 件ずつ順に実行する。
- プローブが期限(既定 5 秒)を過ぎたら:
  1. スーパーバイザは結果 `timeout` を記録する。
  2. そのワーカーを待たずに放棄し、新しいワーカーを起動する。
  3. 詰まったターゲットは、放棄したワーカーが終わるまで打たない(結果 `stuck`)。
  4. 放棄されたワーカーは、呼び出しが返ったら実所要時間を報告して終了する。
- **ロック**: ロックディレクトリ(ローカルのファイルシステム)に、ターゲットごとに
  2 つの空ファイルを置き、`flock` で保持する。ロックは保持するプロセスが生きている間だけ続く。
  - `<target>.lock`: そのターゲットを訪問している間。
  - `<target>.stuck`: 加えて、訪問中のステップが期限を過ぎてから、呼び出しが返るまで。
  - 1 つ目が取れないとき、2 つ目が保持されていれば「詰まっている」(結果 `stuck`、待たない)。
    保持されていなければ他のプロセスが訪問中なだけなので、期限まで待つ。
    待ち切れなければ `skipped`。
  - 詰まったプロセスは 1 ターゲットにつき最大 1 つ。再起動や別の実行をまたいで成り立つ。
  - ワーカーが起動する子プロセス(`lfs`)は 2 つのファイルを継承する。
    ワーカーが先に死んでも、子が詰まっている間はロックが残る。
- **全体の上限**: 詰まっているプローブが上限(既定 16)に達したら、それ以上は何も打たない。
  数えるのは、自分が放棄したワーカーと、ロックディレクトリで `.stuck` が保持されている
  ターゲット(過去の実行の分を含む)の多いほう。
  rpc だけ続ける案は取らない。アイドル切断中のインポートは再接続を待つので、
  サーバが落ちていれば rpc も詰まる。
- **同じサーバのターゲット**: あるターゲットが `timeout` か `stuck` になったら、
  同じ NID の他ターゲットへのプローブを保留する。OSS 停止で一斉に詰まるのを避ける。
  どのステップで保留するかは §15 にある。
- **ワーカーは親から何も引き継がない**: 独立したセッションで起動し、標準入出力は専用のパイプにする。
  親が継承していた記述子は起動前に close-on-exec にする。詰まったワーカーが呼び出し元の
  標準エラーやロックを掴んだままになり、呼び出し元(パイプライン、ssh、cron)が戻れなくなるのを防ぐ。
- **`timeout` はターゲットの責任を意味する**: ワーカーが死んだ、止められた、何も言わなくなった
  場合は `error` とし、保留も掛けない。親が見切ったワーカーは、入力が閉じられたことか、
  親の待ち時間を過ぎたことを検知して、次のステップを始めない。

## 7. 負荷予算とスケジュール

全クライアントが全ターゲットを毎ラウンド打つ設計は取らない。理由は 3 つ。

- 負荷がクライアント数に比例する(Kaleidoscope の 2.42%)。
- OSC は既定 20 秒でアイドル切断する。それより短い間隔で打つと
  クライアント数 × OST 数の接続を張りっぱなしにし、上流が解消した負荷を戻してしまう。
- 「全クライアントが全ターゲットに ping する」こと自体が既知のスケーリング問題である
  (Cray、CUG 2012)。

### 7.1 ターゲットあたりの予算で行列を疎にサンプリングする

- 運用者が決めるのは**フリート全体でのターゲットあたりのレート** B(プローブ/秒)。
- 各クライアントは 1 ティックに 1 ターゲットだけ打つ。ティック間隔は
  `フリート台数 ÷ (B × ターゲット数)`。
- ターゲットの順序はクライアントごとの疑似乱数順列。1 周で全ターゲットを 1 回ずつ打つ。
- 位相はホスト名のハッシュでずらす。遅れても取り戻しのバーストはしない(ティックを捨てて数える)。
- フリート台数は設定値(`--fleet-size`)。自動推定はしない。

例: 1000 クライアント、100 OST、B = 0.5/秒(初期値の案)

| 観点 | 値 |
|---|---|
| クライアント 1 台の data プローブ | 20 秒に 1 回 |
| OST 1 つが受けるプローブ | 毎分 30 回、30 台の別々のクライアントから |
| 同じ(クライアント, OST)の再訪 | 約 33 分に 1 回 |
| MDS が受ける open/close | 毎秒 50 組 |

- 列(ターゲット)の異常は 1 分程度、行(クライアント)の異常は数分で見える。
- セル単位の異常は持続するものしか見えない。これは予算との引き換えとして受け入れる。
- B = 0.5/秒は Kaleidoscope の 2 点(0.1/秒で 0.01% 未満、3.3/秒で 2.42%)の間に置いた
  仮の値で、根拠は弱い。§12 の負荷試験で決め直す。
- 1 万台規模では行の検知が遅くなる。その場合は一部のクライアントだけ参加させる
  (`--participate 1/N`、ホスト名ハッシュで決定)。

### 7.2 接続への影響

- 再訪が 33 分に 1 回なので、接続は 20 秒後にアイドル切断される。張りっぱなしにはならない。
- その代わり、アイドルなクライアントではほぼ毎回再接続が起きる。
  再接続時間は rpc に含まれ、data には含まれない(§4.2 のゲート)。
- rpc のサンプルには、打つ前の接続状態を `conn="warm|cold|unknown"` で付ける。
  状態ファイルは 2.16 まで procfs の 0444、2.17 から debugfs(root のみ)。

## 8. 結果とメトリクス

### 8.1 結果(閉じた集合)

| `result` | 意味 |
|---|---|
| `ok` | 完了して成功 |
| `timeout` | 期限内に返らなかった |
| `disconnected` | rpc ゲートが未接続を返した |
| `inactive` | OSC が無効化されている |
| `error` | その他の errno(`errno_class` で分類) |
| `mismatch` | read の内容が直前の write と一致しない |
| `contended` | プローブ中の実行待ちがしきい値超え |
| `cached` | rpc が RPC を送らずに返った |
| `stuck` | 前のプローブがまだ返っていない |
| `unprepared` | 固定したファイル・ディレクトリが無い、または固定先を確認できない |
| `skipped` | 打たなかった(ゲート不通過、同じサーバの保留、放棄ワーカーの上限など) |

### 8.2 メトリクス

| メトリクス | ラベル | 備考 |
|---|---|---|
| `lustremesh_probe_total` | `fs` `target` `op` `result` | `ok` 以外は発生時だけ系列ができる |
| `lustremesh_probe_duration_seconds_sum` | `fs` `target` `op` | `ok` のみ |
| `lustremesh_probe_slow_total` | `fs` `target` `op` | `ok` のうち `op` ごとのしきい値超え |
| `lustremesh_probe_duration_seconds` | `fs` `kind` `op` | ヒストグラム。ターゲットを畳んだクライアント単位 |
| `lustremesh_target_info` | `fs` `target` `kind` `server_nid` | `ost_conn_uuid` / `mds_conn_uuid` から |
| `lustremesh_target_stuck` | `fs` `target` | 呼び出しが詰まっている間 1 |
| `lustremesh_stall_seconds` | `fs` `target` `op` | 放棄後に返った呼び出しの実所要時間 |
| `lustremesh_workers_abandoned` | — | 現在の放棄ワーカー数 |
| `lustremesh_ticks_skipped_total` | `reason` | 遅延や上限で捨てたティック |

- `op` は `rpc` `write` `read` `open` `mkdir` `rmdir`。
- ターゲット別ラベルの値は sysfs のデバイス名から作る。`hostping` の `orUnknown` と同じ扱いにする。

### 8.3 カーディナリティ

ターゲット別の系列はクライアント数 × ターゲット数に比例する。ここが最大の制約になる。

- (ターゲット, op)あたり定常で 3 系列(`ok` の数、合計、slow)。
- ターゲット別に出す `op` は `write`、`read`、`rpc`。`open` はヒストグラムだけ。
- 1000 クライアント、100 OST、4 MDT なら、(OST 100 × 3 op + MDT 4 × 1 op) × 3 系列 ≒ 91 万系列。
- meta を有効にすると MDT ごとに `mkdir` と `rmdir` が加わるが、MDT は少数なので影響は小さい。
- これを超える規模では、参加クライアントを絞るか、`--target-metrics=off` で
  サーバ(NID)単位の集計に落とす。VictoriaMetrics なら vmagent のストリーム集計で
  ターゲット単位に畳んでから保存する手もある。

## 9. 切り分け(v1 は記録ルール)

単発のプローブはノイズが大きい(Kaleidoscope の指摘)。しきい値の単純比較はしない。

- **窓**: 5 分。
- **列(ターゲット)**: 「そのターゲットで失敗または slow を観測したクライアントの割合」を使う。
  報告クライアント数が下限(例: 5 台)未満なら判定しない。1 台の不調で OST を疑わない。
- **行(クライアント)**: 「そのクライアントが失敗または slow を観測したサーバの割合」を使う。
- **剥がし込み**: 先に広範に失敗しているクライアントを除外してから列を計算する。
- **ピア比較**: 絶対しきい値ではなく、同じ種類のターゲットの中央値との比で判定する。
  HDD とフラッシュの OST を混ぜない(`target_info` に結合する外部ラベルで分ける)。
- **階層の持ち上げ**:
  - 1 つの OST だけ異常 → その OST。
  - 同じ `server_nid` の OST の大半が異常 → その OSS。
  - 大半のクライアントから大半のサーバが異常 → MDS かネットワーク全体。
  - 特定ラックのクライアントだけ異常 → クライアント側ネットワーク(ラックのラベルは外部から付与)。
- **表示**: FleetGrid で `server_nid` → `target` の階層と、ゾーン → ホストの階層の 2 枚。
- **同時推論**(Kaleidoscope の PGM、Deepview の Lasso)は v2 以降のオフライン解析とする。

## 10. 権限と識別

- ワーカーは専用の非特権ユーザー `lustremesh` で動かす。uid はクラスタ全体で揃える
  (LDAP で配布する)。
  root は root squash でファイルシステム上の書き込みに使えないことが多い。
- probe-root は `lustremesh` 所有にし、他ユーザーが書けないようにする。
  ワーカーはディレクトリ fd からの相対パスと `O_NOFOLLOW` で開く。
- 読み取りに特権が要るもの(無くても動くが、機能が落ちる)

| 情報 | 2.12〜2.16 | 2.17 | 無いとき |
|---|---|---|---|
| ターゲット一覧 | `/sys/fs/lustre/{osc,mdc}/` の列挙で足りる | 同左 | — |
| 担当サーバの NID | sysfs、0444 | 同左 | — |
| 接続状態 | procfs、0444 | debugfs | `conn="unknown"` |
| RPC カウンタ | debugfs | debugfs | `cached` 判定が下限値方式になる |

- debugfs を読む場合は `CAP_DAC_READ_SEARCH` だけを付ける。
- **ロックディレクトリ**: 実行ユーザー自身の所有で、他ユーザーが書けないこと(既定のモードは 0700)。
  ロックファイルは 0600 で作り、シンボリックリンクはたどらない。他ユーザーが開けると、
  ロックを握り続けてターゲットを打てなくできる。既定の `/run/lustremesh` は
  tmpfiles.d か systemd の `RuntimeDirectory` で作る。
  ロックは同じディレクトリを使うプロセス同士でしか効かないので、実行ユーザーは 1 つに決める。
- **jobstats**: `jobid_var=procname_uid` ならプロセス名 `lustremesh` でサーバ側に現れる。
  環境変数名を指定しているサイトでは、ワーカーにその変数を設定するオプションを用意する。
  どちらでも、プローブの負荷をサーバ側で分けて見られる。
- **`lustre-ebpf-exporter` との関係**: プロセス名 `lustremesh` は現状 `user` に分類される
  (`DaemonNames` に無く、末尾が `exporter` でもない)。同リポジトリの `DaemonNames` に
  追加する変更が別途要る。

## 11. 既存リポジトリの規約から引き継ぐもの

- 取れなかった値は 0 にしない(`hostping`、`mlxlink_exporter`)。
- 完了した往復だけをサンプルにし、補正値を代用しない(`tcpulse`)。
- `reason` / `result` は閉じた集合にする。
- 一つのターゲットの障害でプロセスを止めない。スクレイプを失敗させない。
- メトリクス名、ラベル、フラグ、ディレクトリ配置(`v1/`)を互換性契約として `AGENTS.md` に書く。

## 14. 決定事項

1. **meta プローブは既定で無効。** changelog 利用者がいないサイトでは有効を推奨する。
2. **ターゲット別メトリクスの `op` は `write`、`read`、`rpc`。** 系列数は §8.3 のとおり。
3. **フリート台数は設定値(`--fleet-size`)。** 構成管理で配る。
4. **専用ユーザー `lustremesh` は LDAP で全ノードに配布する。**

残る不確定要素は §12 の実機確認と、負荷予算 B の既定値(§7.1)だけである。

## 15. M0 の実装状況

`lustremesh check` として次を実装した。Lustre の実機ではまだ動かしていない。
実装後に敵対的レビューを 1 回行い、その指摘を反映してある。

- **対象**: rpc プローブ(§4.1)と data プローブ(§4.2)。meta プローブ、`init`、`agent`、
  メトリクスは未実装。
- **準備**: ファイルは作らない。README の手順で事前に `lfs setstripe -c 1 -o N` しておく。
  無ければ `unprepared`。
- **検証**(ステップ `verify`): 書き込みの前に毎回行う。通らなければ書かない。
  - 自分の所有で、リンク数 1 の通常ファイルであること。サイズを要求しない `statx` で調べる。
  - `lfs getstripe <file>` の出力が、1 ストライプ・`raid0`・目的の OST であること。
    複合レイアウト(PFL、ミラー)や MDT 上のデータは、どの OST にページがあるかを
    1 つの番号で言えないので拒否する。`--no-verify-pin` でこの確認だけ外せる。
  - probe-root 以下のシンボリックリンクはたどらない。
- **プロセスモデル**(§6): 設計どおり。期限の判定はワーカー側の監視タイマーが単独で行い、
  親は `timeout` の通知を受けて放棄する。親側の待ち時間(`--timeout` + 2 秒)を過ぎた
  ワーカーも見切るが、これは `error` であって `timeout` ではない。
- **保留**: `check` は 1 回きりなので、保留は実行の終わりまで続く。
  過去の実行が残した `stuck` も同じ保留を掛ける。

| きっかけ | 保留するもの |
|---|---|
| rpc が `timeout`、またはターゲットが `stuck` | 同じ NID の残りのターゲット全部 |
| verify / write / read が `timeout` | 同じ NID の残りの data(rpc は打つ) |
| MDT の rpc が `timeout` / `disconnected` / `stuck` | 以降の data 全部 |
| open / close が `timeout` | 以降の data 全部 |

- MDT が `inactive` や `error` のときは保留しない。保守で無効化された MDT が 1 つあるだけで
  全 OST の data が止まるのを避ける。
- **`cached` の判定**(§4.1): debugfs のカウンタが読めればそれで判定する。読めなければ
  `--rpc-floor`(既定 0 = 無効)で判定し、無効のときは「RPC を送ったか未確認」と報告する。
  マウント後最初の statfs はカウンタの行がまだ無いので、root でも未確認になる。
  `cached` や未確認の `ok` でもゲートは通す。約 2 秒以内に応答があったという意味だからである。
- **`contended` の判定**(§4.4): 実行待ちが `--contended-floor`(既定 50µs)以上、かつ
  所要時間の `--contended-ratio`(既定 0.1)以上。どちらも仮の値。
- **`mismatch`**: 読み返したページが別のプローブの書いたページなら、破損ではなく
  クライアント ID の重複としてメッセージを分ける。
- **接続状態**: rpc の直前に読んだ状態をそのまま表示する(`conn` ラベルへの変換は M1)。
- **依存**: 標準ライブラリと `golang.org/x/sys`(`statx` のため)。
